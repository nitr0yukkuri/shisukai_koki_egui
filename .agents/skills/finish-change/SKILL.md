# 変更を仕上げる

このスキルは、実装や修正が終わったあとに「PRに出せる状態」まで持っていくために使う。

## 方針

- Issue は1つの責務を基本にする。
- PRは必要なら複数Issueや複数レイヤーを横断してよい。
- ルールを守るためだけの作業は増やさない。
- コードから分かることを、理由なくドキュメントへ重複して書かない。
- 重要な設計判断を変更した場合だけ、既存ADRとの整合を確認する。
- プロダクト要件が未決定の領域は勝手に確定しない。
- CodeRabbitは補助。最終判断やmerge可否をCodeRabbitだけに依存しない。

## 手順

1. 変更差分を確認する。
   - 関係ない変更が混ざっていないか見る。
   - 変更の目的を一文で説明できる状態にする。

2. 検証する。
   - `bash .agents/skills/finish-change/scripts/verify.sh` を実行する。
   - 失敗した場合は、原因を確認して今回の変更範囲で直せるものだけ修正する。
   - 無関係な既存不具合まで勝手に直さない。

3. ドキュメント影響を確認する。
   - コマンド、外部仕様、アーキテクチャ判断が変わった場合だけ関連ドキュメントを更新する。
   - 「念のため」だけで新しいdocsを増やさない。

4. PR向けに整理する。
   - 変更内容を短くまとめる。
   - 関連Issueがあれば記載する。
   - 実行した検証と結果を書く。
   - 補足がなければ補足欄を無理に埋めない。

5. Git操作を行う場合。
   - assistantが作るコミットメッセージは日本語にする。
   - branch名は変更内容が分かる程度でよい。
   - mergeはユーザーが明示的に依頼した場合だけ行う。

## 完了条件

- 変更の目的と差分が一致している。
- 検証結果を説明できる。
- 不要なドキュメントやルールを増やしていない。
- PR本文に「やったこと」「関連Issue（あれば）」「動作確認」を書ける。
