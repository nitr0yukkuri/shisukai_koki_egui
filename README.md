# じょぶはん

面接・面談で話したことを、次につながる振り返りに。

じょぶはんは、面接・面談の練習や振り返りを支援するWindowsデスクトップアプリです。AIが面接官の代わりに質問や評価を行うことを主目的とせず、本人の発話を記録・整理し、何を伝えたかや話し方を振り返る材料をつくります。まずは一人での練習を中心にし、将来的には1対1の面接・面談後の振り返りにも広げることを検討します。

履歴書・エントリーシート（ES）は、本人の経験や志望内容をAIが理解するためのコンテキストとして、本人が選んだ場合に利用します。本人の発話の要約や助言を具体化するための材料であり、AIに面接官役をさせるためのものではありません。

Zoomとは独立したアプリとして起動します。Zoom画面にオーバーレイを重ねたり、Zoomの映像を取得・加工したりするアプリではありません。

授業の4人チーム開発用リポジトリです。

## 解決したいこと

- 面接で緊張して、うまく話せなくなる
- 一人では面接練習を始めにくい
- 「あー」「えー」などの言い淀みや、話す速さ・間に自分では気づきにくい
- 練習後に回答を振り返る材料が残らない
- 自分の経験や志望内容を踏まえて、話した内容を振り返るのが難しい

じょぶはんは、練習中の補助だけでなく、終了後に自分の発話を見返し、伝えた内容や次に試すことを整理する機会をつくります。

## 使い方のイメージ

### 一人で練習する

質問カードや自分で用意した質問に声で回答します。質問は練習を始めるためのきっかけで、中心は本人の発話を記録・整理し、回答内容や話し方を後から振り返ることです。必要に応じてヒントも使えます。

### 相手と練習する

キャリアセンターの相談員や友人などと、Zoom等を使って1対1で練習します。初期段階では、相手にアプリを入れてもらう必要はありません。アプリが扱う音声は練習する本人のマイク入力のみで、相手の音声は取得・記録しません。

このため、初期段階のログは質問と本人の回答、または本人の発話が中心です。双方の発言を記録する会話ログは、相手の同意や保存方法を設計したうえで将来の候補とします。

### 練習の支援を段階的に減らす

- **練習モード**: 質問カードやヒントを見ながら練習する
- **ヒント少なめ**: 必要なときだけ補助を使う
- **本番想定モード**: 練習中のヒントを抑え、終了後に振り返る

ここでいう「本番想定」は練習方法の一つであり、実際の選考中にアプリを使うことを目的としません。

## 初期版で優先する機能

- 質問カードを使った一人用の面接練習
- 本人のマイク音声の文字起こしと、認識結果の確認・修正
- 詰まったときに任意で確認できるヒント
- 練習ログの端末内保存、検索、編集、削除
- ヒントの量を切り替え、練習後に振り返る機能

音声認識には誤認識や聞き落としがあるため、文字起こしは本人が確認・修正できるようにします。AIの振り返りは参考情報とし、面接の合否、本人の適性や人格を判定するものではありません。

## 今後検討する機能

- 練習後に、話速・無音区間・「あー」「えー」などのフィラー候補を振り返る。算出方法・検出精度・該当箇所の確認方法（音声の保存・再生範囲を含む）を検証してから追加する。
- 履歴書・ESを本人の経験や志望内容を理解するコンテキストとして使い、本人の発話の要約や振り返りを具体化する
- 回答の要点・重要キーワード・次回確認したいことを整理する
- 本人の回答を履歴書・ESの内容と照らし、違いの可能性を断定せず、本人が確認する候補として示す
- ログ中で選択した単語の解説や、重要キーワードの強調
- 企業についてのチェック項目・メモ・逆質問の管理
- 相手の同意を得たうえでの相手側の発話ログやフィードバック

AIの役割は面接官の代替や合否判定ではなく、本人の発話を整理し、本人が振り返るのを助けることです。履歴書・ESは本人の背景を理解するコンテキストとして使い、AIモデルの追加学習には使わない想定です。AIが出す要約・助言や書類との違いは参考情報とし、食い違いを虚偽や矛盾と決めつけず、本人が確認する候補として示します。AI機能を導入する場合は、送信する内容・送信先・保存方法を明示し、ユーザーが確認してから使える設計を検討します。

## デザイン方針

練習を続けやすく、必要な情報を見つけやすい画面を目指します。かわいいテーマや恋愛ゲーム風の表現は、緊張を和らげて練習を始めやすくするための任意のデザイン要素です。恋愛要素はアプリの主目的ではなく、企業や面接相手を恋愛対象として扱ったり、好感度で合否を表したりすることを目指しません。

## 練習ログ・プライバシー

- 初期段階では本人のマイク音声のみを扱い、相手の音声は取得しません。
- 音声処理とログ保存は端末内で行う方針です。音声認識方式や保存方式は技術検証を進めます。
- 音声を保存するか、文字起こしだけを保存するかを明確にし、ログはユーザーが削除できるようにします。
- AI機能を導入する場合、履歴書・ESや回答内容などを外部へ送信する前に、送信内容と送信先を確認できる設計を目指します。
- 相手と練習する場合は、アプリの利用と音声の扱いを事前に伝えます。

## 技術構成（暫定）

- **デスクトップアプリ**: Windows向けにElectron + React + TypeScriptで開発します。Reactで画面（renderer）を構築し、ElectronでWindowsデスクトップアプリとして動作させます。
- **練習ログ**: 初期版は端末内のSQLiteに保存し、クラウド同期は行いません。
- **音声認識**: PC内で処理する方針です。日本語の認識精度や言い淀みの検出精度を比較して方式を選びます。
- **バックエンド**: 初期版のローカル練習には設けません。外部AI APIを使う段階で、APIキーをデスクトップアプリに含めないためのNode.js + TypeScript + Express APIを追加する想定です。
- **型の共有**: デスクトップアプリとExpress APIでリクエスト・レスポンスの型を共有します。TypeScriptの型だけでは実行時の入力を検証できないため、API境界には実行時バリデーションも設けます。
- **クラウドDB**: 現時点ではCloudflare D1もSupabaseも採用しません。ログインや端末間同期が必要になった時点で再検討します。Cloudflare D1を選ぶ場合はWorkersを含む構成、Supabaseを選ぶ場合はPostgresやAuthを使う必要性も合わせて判断します。

履歴書・ESを使うAI機能は、書類をモデルの追加学習に使うのではなく、本人の発話を理解し、要約・振り返りを具体化するコンテキストとして使う想定です。外部送信の対象・送信先・同意方法を決めてから導入します。

旧オーバーレイ案やSupabaseを前提とした資料・ADRは、現在の暫定方針を確定するものではありません。

## Development policy

- 1 Issue = 1つの責務を基本にする
- 大きな設計判断は ADR に残す
- CodeRabbit は補助レビュアーとして使う
- test / lint / build など再現可能なCIを客観的な品質ゲートにする
- 4人チームなので、過度な分散システム化より責務境界の明確さを優先する
- 面談中に視線移動・操作が増えすぎないよう、質問・ヒント・ログ・振り返りの情報設計を優先する

## Status

現在は企画と技術検証を進めています。ここに記載した機能には、今後の検討段階のものが含まれます。音声認識の精度、言い淀みの検出方法、AIへ送る情報、ローカル保存とクラウド保存の選択は、Issue / ADRで合意してから実装します。

## Development commands

よく使う開発コマンドは Makefile にまとめています。

    make help
    make setup
    make run
    make fmt
    make test
    make lint
    make build
    make check

現時点ではElectron / Node.jsプロジェクトの初期化前です。上記のMakefileコマンドは旧Go基盤の仮置きであり、package.json、Electronのメインプロセス、レンダラープロセスの初期化時に更新します。
