### A-1. utterances の保存タイミングが内部設計書の中で逆になっている

**問題**

| 箇所 | 記述 |
| --- | --- |
| §5-4（回答中） | 確定した分を **utterances に即時保存**する |
| §11.2-3（回答中） | 認識結果はメモリに持ち、**この間はDBに書かない** |

同じ処理を正反対に書いている。実装は §11.2 に従い、回答終了時に1トランザクションでまとめて保存している。

**改善案**

§5-4 を §11.2 に合わせて「確定した分はメモリに持ち、`stt:final` として画面へ送る。DBへの書き込みは
回答終了（§5-6）の1トランザクションで行う」に書き換える。あわせて NFR-08「回答ごとに即時保存」の
「即時」が**ターン単位**を指すことを、要件定義書か内部設計書 §5 に一文で補う。

**可否：📝 設計書を直す（実装は変えない）**

**判断理由**

ターン単位の確定保存で NFR-08 の目的（異常終了しても直前の回答まで残る）は満たせている。
発話ごとに書くと、回答のやり直し時に書いた行を消す処理（現 `clearTurnRecords`）が回答中にも必要になり、
トランザクションが細切れになって「1回の回答＝1つの原子的な記録」という §5-6 の設計が崩れる。
§11.2 の記述のほうが設計として一貫しており、実装もそれに従っている。

### A-2. NFR-02 と音声認識の待ち時間が両立しない

**問題**

- NFR-02：回答終了から次の質問表示まで **1秒以内**
- §5-6・§11.2-5：回答終了後、認識の最終結果を **最大約5秒**待つ

利用者から見た「回答終了ボタン→次の質問が出る」までに最大5秒かかるため、文面どおりでは必ず違反する。

**改善案**

NFR-02 を2つに分ける。

| ID | 対象 | 目標 |
| --- | --- | --- |
| NFR-02a | 回答の確定（`practice:endAnswer`） | 認識の最終結果を最大5秒待つ。1秒を超えたら「文字起こしを確定しています」の待ち表示を出す |
| NFR-02b | 次の質問の表示（`practice:next`） | 押してから質問文が出るまで1秒以内 |

**可否：📝 設計書を直す（実装は変えない）**

**判断理由**

待ち時間の実体は音声認識サービス側の応答であり、アプリ側では短縮できない。
5秒の上限（`SpeechService.finalWaitMs`）は既に実装済みで、これを1秒に縮めると発話の末尾が欠ける。
測れない目標を残すより、計測点を分けて現実的な値を置くほうがよい。
外部設計書 §5.4 の状態遷移（「回答終了後（確認）」という状態がある）とも整合する。

### A-3. エラーコード3種に対応するメッセージがない

**問題**

内部設計書 §4.3 のエラーコードは9種（E_VALIDATION / E_MIC / E_STT / E_ASSIST / E_EVAL / E_CONSENT /
E_KEY / E_NET / E_DB）。一方 §9.1 には「想定外の例外は**汎用のエラーとして**返す」とあるが、そのコードが
定義されていない。実装は運用上必要な3つを追加している。

| コード | 実装での用途 | 対応するMSG |
| --- | --- | --- |
| `E_STATE` | 進行中の練習がある／回答中でない等、操作の順序が不正 | **なし** |
| `E_NOT_FOUND` | ES・練習ログが見つからない | **なし** |
| `E_UNEXPECTED` | 想定外の例外（§9.1 の「汎用のエラー」） | **なし** |

**改善案**

内部設計書 §4.3 の表に3行を追加し、外部設計書 §7 にメッセージを追加する。

| ID | タイミング | 表示する文言（案） | 操作 |
| --- | --- | --- | --- |
| MSG-15 | 操作の順序が不正（E_STATE） | この操作はいまできません。画面を読み込み直してください | OK |
| MSG-16 | 対象が見つからない（E_NOT_FOUND） | 対象のデータが見つかりません。削除された可能性があります | 一覧へ戻る |
| MSG-17 | 想定外のエラー（E_UNEXPECTED） | エラーが発生しました。もう一度お試しください | もう一度 |

**可否：🔧📝 両方（設計書に3コード＋3MSGを追加。実装は renderer 側にMSG対応表を持たせる）**

**判断理由**

コード自体は実装が勝手に増やしたものではなく、§9.1 が要求している内容を具体化したにすぎない。
ただし文言は「renderer 側だけが持つ」（§9.1）決まりなので、外部設計書で文言を決めないと画面が作れない。
MSG番号は外部設計書の連番の続き（MSG-15〜17）とし、内部設計書 §4.3 の対応表を更新する。

### A-4. PracticeSessionService の責務が過大

**問題**

§3.1 は PracticeSessionService に「練習の開始・回答開始/終了・次の質問・終了・中断」に加えて
「**過去の練習の一覧・詳細・削除と、回答の文字起こしの修正**も受け持つ」と書いている。
しかし §10.1 のディレクトリ構成にその姿は現れず、§3 の「サービス同士は呼び合わない」方針とも噛み合わない。
実装では履歴機能を `HistoryService` に分離している。

**改善案**

§3.1 の表を実装に合わせる。

- `PracticeSessionService` … 練習の状態遷移のみ（FR-13〜15）
- `HistoryService` … 練習ログの一覧・詳細・削除・文字起こしの修正（FR-08・09・16・29）を**新規行として追加**

§10.1 の `services/` の並びにも `History` を足す。

**可否：📝 設計書を直す（実装は変えない）**

**判断理由**

履歴の参照は練習の状態遷移を一切必要としない。同じサービスに入れると、
状態を持つクラス（`active` フィールド）が状態を持たない参照系まで抱えることになり、
テストでも毎回練習を開始しないと履歴を読めなくなる。実装の分離のほうが §3 の
「依存の向きは一方向」に忠実で、現に `HistoryService` は `SessionRepository` だけに依存している。

### A-5. マイグレーション失敗時の復元手順が未定義

**問題**

§8.5 に「適用の前にDBファイルを `jobuhan.db.bak` へ写す。**失敗したら元へ戻し**、E_DB を画面に出して、
練習は始めさせない」とあるが、「元へ戻す」のが誰か（アプリの自動処理か、利用者の手作業か）、
いつ戻すのかが書かれていない。実装は `.bak` を作り、失敗時はその場所を含むメッセージで E_DB を返すだけで、
自動復元はしない。

**改善案**

§8.5 を次のように具体化する。

1. 控えは、**適用すべき版があり、かつ既存のDBがあるときだけ**作る（新規インストール時は作らない）
2. 失敗してもアプリは**自動で戻さない**。E_DB と控えの場所を画面に出し、練習を始めさせない
3. 復旧は利用者の操作（または次版での移行処理）で行う

**可否：📝 設計書を直す（自動復元は実装しない）**

**判断理由**

自動で `.bak` へ差し戻すと、失敗の原因（壊れたSQL・ディスク不足）が残ったまま次回起動で同じ
マイグレーションを再実行し、失敗と復元を繰り返す。利用者のデータを黙って巻き戻す操作でもある。
「止めて知らせる」ほうが安全側で、実装もその方針になっている。

> 補足：この調査と並行して、WALモードでは直前のコミットが `-wal` 側に残り控えが古くなる不具合を
> 実装側で修正済み（複製の前に `PRAGMA wal_checkpoint(TRUNCATE)` を挟む）。
> §8.5 にもこの手順を一文入れておくとよい。

### B-3. 文字数超過で保存できない（最優先）

- FR-04「空欄・文字数超過を**警告する**（練習は空欄だけでも開始可能）」
- 外部設計書 §5.2「文字数の上限は仮。超えたときは**赤字で警告するが保存はできる**（FR-04）」
- MSG-02「文字数が上限を超えています。**このまま保存できますが**、評価では途中までを使います」

資料は3箇所で「超過しても保存できる」と明記している。実装は `esSetInputSchema` の
`z.string().max(ES_BODY_MAX_LENGTH)` と `EsService.save()` の長さチェックで `E_VALIDATION` を返し、
**保存を拒否する**。書きかけの長いESが保存できず、MSG-02 を出す場面そのものが発生しない。

**改善案**

1. `esSetInputSchema` の本文 `.max()` を、**DB肥大の歯止めとしての絶対上限**に置き換える
   ```ts
   /** これを超えたら E_VALIDATION。貼り付け事故への歯止めで、画面の上限とは別。 */
   export const ES_BODY_HARD_LIMIT = 20000;
   ```
2. `EsService.save()` の本文長チェック（`E_VALIDATION`）を削除する。セット名の必須チェックは残す
3. 画面（SC-02）が `ES_BODY_MAX_LENGTH[kind]` と比較して赤字警告と MSG-02 を出す
4. 超過分の扱い（AIへ送るときの切り詰め）は C-2 で決める

**可否：🔧 実装を直す**

**判断理由**

**資料の3箇所が一致して「保存できる」と定めており、解釈の余地がない。実装が仕様違反である。**
面接練習アプリで「上限を超えたので保存しません」は、利用者が書いた文章を失わせる最悪の挙動であり、
FR-04 がわざわざ「警告する」と書いた意図に正面から反する。
絶対上限（20000字）を別に置くのは、貼り付け事故でDBが肥大するのを防ぐためで、
設計書の意図（画面で制限）とは矛盾しない。

> **2026-11-13 追記：この改善案がそのまま仕様になった。** 外部設計書 §5.2 に
> 「1項目 20000文字を超える本文は保存できない（MSG-18）」、内部設計書 §4.3 の
> E_VALIDATION に「ES本文のハード上限20000文字。**文字数の上限超過はエラーではなく
> 警告（MSG-02）のみ**」が明記され、MSG-18 も新設された。

### B-6. PRAGMA が3つ未設定（最優先）

**問題**

内部設計書 §8.1 とテーブル定義書 table_view が、接続のたびに設定する PRAGMA を5つ挙げている。
実装（`src/main/db/database.ts`）は先頭2つだけ。

| PRAGMA | 設計書 | 実装 |
| --- | --- | --- |
| `foreign_keys = ON` | 必須 | ✅ |
| `journal_mode = WAL` | 必須 | ✅ |
| `synchronous = NORMAL` | 必須 | ❌ |
| `busy_timeout = 5000` | 必須 | ❌ |
| `secure_delete = ON` | 必須 | ❌ |

**改善案**

`openDatabase()` の初期化に3行を足す。

```ts
connection.exec("PRAGMA foreign_keys = ON;");
connection.exec("PRAGMA secure_delete = ON;");
connection.exec("PRAGMA busy_timeout = 5000;");
if (filePath !== ":memory:") {
  connection.exec("PRAGMA journal_mode = WAL;");
  connection.exec("PRAGMA synchronous = NORMAL;");
}
```

5つとも node:sqlite 3.50.2 で設定できることを実機で確認済み（付録参照）。

**可否：🔧 実装を直す**

**判断理由**

**`secure_delete = ON` は FR-29（データ削除）の根拠そのもの。** 内部設計書 §8.1 は
「SQLite は行を消しても中身をファイルに残す（**実測：消したESの本文がDBファイルに残った**）」と
実測を添えてこの設定を要求している。未設定のままでは、利用者が削除したESや会話ログの本文が
`jobuhan.db` に残り、NFR-09（PC内に保存し外部に出さない）の前提で守っているはずのプライバシーが崩れる。
`synchronous = NORMAL` は WAL との組み合わせで推奨される既定、`busy_timeout` は
マイグレーション検証用の一時DBなど将来の複数接続に対する保険で、いずれも副作用がない。

> **2026-11-13 追記：要求が1つ増えた。** 改訂版の内部設計書 §8.4 に
> 「削除のあとは `PRAGMA wal_checkpoint(TRUNCATE)` を実行して、削除した内容が
> `-wal` ファイルに残らないようにする」が加わった。`secure_delete = ON` は本体ファイルしか
> 守らないという正しい指摘で、`history:delete` と `es:delete` の成功後にチェックポイントを
> 打つ必要がある。この1行が A-5 で直したマイグレーション時の処理と同じ仕組みなので、
> 共通の関数（例：`AppDatabase.checkpoint()`）にして両方から呼ぶとよい。

### B-7. STRICT テーブルになっていない

**問題**

内部設計書 §8.1「SQLite は型違いの値も通してしまうので、表は **STRICT** で作る」、
テーブル定義書 table_view「表はすべて STRICT で作る（型違いの値を弾く）」。
実装の `0001-init.ts` に `STRICT` がない。

**改善案**

`0001-init.ts` の各 `CREATE TABLE` 末尾に `STRICT` を付ける（全14表）。

**あわせて必要な対応（重要）**：STRICT 下では小数を INTEGER 列に入れると**実行時エラーになる**
（実機確認：`cannot store REAL value in INTEGER column`）。
現在の Fake は整数の ms しか返さないため問題は出ないが、
**実際の音声認識サービス（U-06）が小数の時刻を返すと保存に失敗する**。境界で丸める処理を入れておく。

```ts
// SpeechService で認識結果を受け取るとき、または Repository の insertUtterance / insertFillerEvent で
startMs: Math.round(word.startMs)
```

**可否：🔧 実装を直す**

**判断理由**

2つの資料が明記しており、node:sqlite（SQLite 3.50.2）で問題なく作成できることを確認済み。
STRICT が実際に防ぐのは「`'abc'` を INTEGER 列へ」「`1.5` を INTEGER 列へ」といった
**静かに壊れるデータ**で、非STRICTではどちらも通ってしまう（付録参照）。
`words_json` を経由して外部サービスの値がそのままDBに入る設計なので、
この防御は U-06 を接続したあとに効いてくる。
いまはリリース前で既存データがないため、`0001-init.ts` を直接書き換えてよい
（§8.5「開発中は列の追加を許す」の範囲。開発機のローカル `jobuhan.db` は削除して作り直す）。

## 付録：実機で確認した事項

Node.js の `node:sqlite`（SQLite **3.50.2**）で検証した。

### PRAGMA（B-6）

`foreign_keys = ON` / `journal_mode = WAL` / `synchronous = NORMAL` / `busy_timeout = 5000` /
`secure_delete = ON` の5つすべてが設定でき、設定後の読み出しでも反映を確認。

### STRICT（B-7）

`STRICT` 付きの表を作成でき、型の扱いは次のとおりだった。

| 操作 | STRICT | 非STRICT |
| --- | --- | --- |
| `'abc'` を INTEGER 列へ | **弾く** | 通る |
| `1.5` を INTEGER 列へ | **弾く** | 通る |
| `'123'` を INTEGER 列へ | 通る（可逆な変換） | 通る |
| `123` を TEXT 列へ | 通る（TEXTへ変換） | 通る |
| 整数 `279` を REAL 列へ | 通る | 通る |
| 小数 `279.2` を REAL 列へ | 通る | 通る |

→ STRICT が防ぐのは「静かに壊れるデータ」。
ただし **小数の ms を INTEGER 列に入れると実行時エラー**になるため、
U-06 で実サービスを接続する際は `Math.round()` を境界に入れること（B-7 の改善案）。

### CHECK 制約（B-8）

`seq >= 1` / `filler_count >= 0` / `total_score BETWEEN 0 AND 100` の3つとも、
範囲外の値を期待どおり弾いた。`total_score = 100` は通る。

### json_extract（B-10）

`json_extract('{"name":"A社"}','$.name')` が `A社` を返すことを確認。
`es_snapshot_json` からのセット名の取り出しに使える。
