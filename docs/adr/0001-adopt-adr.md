# ADR-0001: 設計判断をADRとして記録する

- Status: Accepted
- Date: 2026-09-22

## Context

このプロジェクトでは、Go、DB、Queue、Worker、Kubernetes、CI/CD など複数の技術選定や設計判断を行う予定です。

コードだけでは「何を選んだか」は残っても、「なぜその選択をしたか」「何を比較したか」「どんな欠点を受け入れたか」が後から分からなくなる可能性があります。

また、4人で開発するため、設計判断の理由を共有できる形にしておく必要があります。

## Decision

重要なアーキテクチャ・技術選定は Architecture Decision Record（ADR）として `docs/adr/` に記録します。

ADR には最低限、次を残します。

- Context
- Decision
- Alternatives
- Consequences
- Validation

Accepted になった ADR の結論を後から直接書き換えて歴史を消さず、判断を変更する場合は新しい ADR を追加します。

## Alternatives

### README や Issue にだけ理由を書く

良い点:

- ファイルが増えない
- その場では手軽

悪い点:

- Issue が閉じた後に設計判断を探しづらい
- README が技術判断の履歴で肥大化しやすい
- 判断が変わった経緯を追いにくい

### コードだけを正とする

良い点:

- ドキュメント更新コストがない

悪い点:

- 実装から判断理由や比較対象までは分からない
- 将来「なぜこの構成なのか」を再検討しにくい

## Consequences

良い点:

- 技術選定の理由を後から確認できる
- 新しいメンバーや未来の自分が設計意図を理解しやすい
- 採用しなかった案とトレードオフも残せる
- 設計変更の履歴を追える

受け入れるデメリット:

- 設計変更時に ADR を書く手間が増える
- 小さな判断まで記録すると運用が重くなる

そのため、すべての実装判断ではなく「後から理由を知りたくなりそうな重要な判断」だけを ADR の対象にします。

## Validation

プロジェクトの中盤・終了時に、次を確認します。

- 技術選定の理由を ADR から説明できるか
- 古い判断と新しい判断の経緯を追えるか
- ADR の作成自体が開発のボトルネックになっていないか

運用コストの方が大きい場合は、ADRを書く対象をさらに絞ります。
