# 用語集

このドキュメントは、チーム内で技術用語の意味を揃えるためのものです。
一般的な定義に加えて、このプロジェクトで何に使うかも書きます。

## Worker

Queue に積まれた仕事を取り出して、バックグラウンドで処理する実行担当。

このプロジェクトでは、HTTP リクエスト中に完了させる必要がない重い処理を API から分離する場合に使います。

```text
API -> Queue -> Worker -> DB
```

## Queue

処理待ちの Task を一時的に保持し、API と Worker を疎結合にする仕組み。

大量リクエストを一度に Worker へ流さず、処理能力に合わせて順番に捌くために使います。

## Task

Worker に処理してほしい仕事を表すデータ。

Task ID、処理種別、必要な入力などを持ち、重複配送や retry を考慮できる形にします。

## Docker

アプリケーションと実行環境をコンテナとしてまとめる仕組み。

チームメンバー間で「自分のPCでは動く」を減らすために使います。

## Docker Compose

API、DB、Queue、Worker など複数コンテナをまとめて起動する仕組み。

ローカル開発環境を 1 コマンドで再現するために使います。

## Kubernetes / K8s

コンテナを複数台で動かし、再起動、配置、更新、スケーリングなどを管理する基盤。

このプロジェクトでは、API と Worker を別々にデプロイし、負荷に応じて Worker を水平スケールする実験に使う予定です。

## Pod

Kubernetes 上で動く最小の実行単位。

このプロジェクトでは API Pod、Worker Pod のように扱います。

## Deployment

Pod の個数や更新方法を宣言的に管理する Kubernetes リソース。

API と Worker を独立して増減できるようにします。

## Service

Kubernetes 内の Pod への安定したアクセス先を提供する仕組み。

Pod が作り直されて IP が変わっても、API への接続先を固定するために使います。

## HPA

Horizontal Pod Autoscaler の略。

CPU やメモリなどの指標をもとに Pod 数を自動で増減させます。

## KEDA

Kubernetes Event-driven Autoscaling の略。

Queue backlog などイベント量をもとに Worker 数を増減させたい場合の候補です。

## CI

Continuous Integration の略。

PR ごとに test、lint、build などを自動実行し、変更が壊れていないか確認します。

## CD

Continuous Delivery / Deployment の略。

CI を通過した成果物を、決めた環境へ自動で届ける仕組みです。

## GitHub Actions

GitHub 上で CI/CD の workflow を実行する仕組み。

このプロジェクトでは test、lint、build、将来的には deploy を担当します。

## CodeRabbit

Pull Request の差分を AI でレビューするツール。

このプロジェクトでは、アーキテクチャ境界、テスト不足、エラー処理、非同期処理の観点などを補助的にレビューさせます。
merge 可否の最終判断や test の実行結果は CodeRabbit に依存しません。

## ADR

Architecture Decision Record の略。

「何を選んだか」だけでなく、「なぜ選んだか」「何を捨てたか」「どんな欠点があるか」を残す設計判断の記録です。

## モジュラーモノリス

1つのアプリケーションとしてデプロイしつつ、内部を責務ごとのモジュールへ分離する構成。

4人チームで過度に分散システム化せず、コード境界を意識するための候補です。

## OpenAPI

HTTP API の仕様を機械可読な形式で記述する規格。

Frontend と Backend の契約を明示し、並行開発しやすくするために使う予定です。

## 冪等性 / Idempotency

同じ操作が複数回実行されても、意図しない重複結果を生まない性質。

Queue は同じ Task を再配送する可能性があるため、Worker 実装で特に重要です。

## Retry

失敗した処理を再実行する仕組み。

何でも無限に再実行するのではなく、対象エラー、回数、待機時間、最終失敗時の扱いを決めます。

## Graceful Shutdown

プロセス終了時に新規受付を止め、処理中の仕事や接続を安全に閉じてから終了すること。

API や Worker が Kubernetes 上で再起動される場合にも重要です。

## Latency

1つのリクエストや処理が完了するまでの時間。

k6 の負荷試験で評価します。

## Throughput

一定時間あたりに処理できる量。

例: requests/sec、tasks/sec。

## p95

全体の 95% がその値以下に収まることを示す percentile。

平均値だけでは隠れやすい「遅いリクエスト」を見るために使います。

## k6

負荷試験ツール。

同時アクセスを再現し、latency、throughput、error rate などを測定します。

## コンウェイの法則

組織のコミュニケーション構造が、作られるシステムの構造に反映されやすいという考え方。

## 逆コンウェイ戦略

作りたいアーキテクチャの境界に合わせて、チームの責務やコミュニケーション構造を設計する考え方。

このプロジェクトでは4人しかいないため、完全分業ではなく「主担当を置きつつ全員がレビューできる」程度に試します。
